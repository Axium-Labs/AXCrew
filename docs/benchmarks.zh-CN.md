# AXCrew 分布式基准测试

[English](benchmarks.md) | **简体中文**

外部的 [AX-Bench Agent 包](https://github.com/Axium-Labs/AX/blob/main/benchmarks/agent/README.md) 测量生产版 Crew 与 AX 工作进程，不改变 Crew 的调度、租约、权限或持久化行为。[分布式控制器配置](https://github.com/Axium-Labs/AX/blob/main/benchmarks/agent/docs-crew.md) 说明真实节点管理、DAG、产物校验、故障/恢复与采集器。

控制器支持专用的本地或 SSH 工作进程，启动、停止、崩溃和网络钩子均显式限定在本次运行内。随附的自有工作进程辅助工具在发送进程信号前，会检查保存的 PID 与进程创建标识，并保留执行数据。节点配置必须明确给出，不会推断云资源准备方式，也不使用模拟工作进程。任务别名会转换为原生 Workflow/依赖标识；同级任务并发提交，实际执行并发度则另行观察。

确定性检查覆盖实际任务 JSON、不可变产物字节及验证器、提交幂等性与冲突拒绝、Workflow 检查点 CAS、实际观察到的执行尝试代次/所有者围栏隔离，以及依赖执行顺序。只有存在真实故障回执，才会为恢复评分；没有触发故障不算测试成功。资源与 Provider 使用量由声明的只读采集器提供，并保留其进程/网络范围；不可用值保持为 null。

应使用专用 Crew 服务器、基准项目和隔离的工作进程工作区。适配器只取消自己创建的任务，并在清理时恢复已配置的节点故障。每个场景至少重复 3 次；与父 Runner 集成时避免把外层三次重复再乘成九次。JSON/CSV/Markdown 报告保留快照、节点/故障事件、失败、源码/模型标识和测量边界。

单主机执行、多个逻辑 Host ID、由操作者确认的物理机器指纹，属于不同范围。多个 Host ID 本身不能证明存在多台物理机器。状态断言覆盖观察到的历史，不是对所有分布式交错执行的形式化证明。离线规划或控制器回归测试夹具不会产生能力/分布式评分。
